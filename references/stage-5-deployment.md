# Stage 5 — Deployment: Technique Reference

Technique guidance supported by public documentation and website sources. This file supports aspects 5.1–5.6 of `SKILL.md`.

## Design plan and execution evidence

For a new project, specify executable checks with environment/version, case or fixture, runner/procedure, expected evidence, inherited acceptance criterion, owner and run point. Attach actual results from an existing implementation or authorized pilot; otherwise record pending execution and the gate that blocks adoption or exposure. Document approval approves the design plan. Required calibration, capacity, security and recovery checks must actually pass before their corresponding production action or traffic exposure.

## Release strategy and gray rollout (5.1)

**Comparable canary.** Expose the candidate to a risk-appropriate subset of eligible traffic while retaining a comparable control. Record cohort assignment, comparability factors, initial allocation, exposure stages and collection windows in the rollout plan. The comparison decision references the applicable quality, safety, latency, cost and reliability measures and minimum-evidence verdict from Stage 4. Link each exposure stage to the release-action table in 5.6 so one operational owner acts on the collected evidence. [Google SRE canarying](https://sre.google/workbook/canarying-releases/) and [Argo Rollouts analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/) (current, accessed 2026-09-30).

**Exposure prerequisites.** For the first launch and later changes, identify the Stage 4 offline verdict, deployed-control evidence and exposure authorization required before each traffic increase. Record their evidence IDs, readiness disposition and exposure owner in the rollout evidence-readiness table. Link live observations to 6.4 and reviewed failures to the 6.1 intake; those owners maintain monitoring and improvement work. [Google SRE canarying](https://sre.google/workbook/canarying-releases/) (current, accessed 2026-09-30).

**Content-risk comparison.** Use the deployed labeled-test and adversarial results from 5.5 when choosing rollout comparisons. Record which approved missed-violation and false-block measures can be compared reliably by cohort and which severe or rare risks need offline evidence. The readiness table links that evidence to the applicable Stage 4 safety verdict and 5.6 release action. [Microsoft Content Safety transparency note](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/content-safety/transparency-note) (current, accessed 2026-09-30); [Google SRE canarying](https://sre.google/workbook/canarying-releases/) (current, accessed 2026-09-30).

**Recovery readiness.** At document approval, record each 5.6 recovery-action ID, executable revert-test plan, expected evidence, stored-state compatibility check, accountable evidence-readiness owner and separate exposure owner. Attach existing results or label execution pending. Before corresponding traffic exposure, require passing compatibility/recovery evidence; 5.6 owns revert and external-effect reconciliation or compensation procedures. [Google SRE canarying](https://sre.google/workbook/canarying-releases/) and [Azure compensating transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction) (current, accessed 2026-09-30).

## Serving and inference acceleration (5.2)

**Workload indicators.** Specify workload and accepted-load measurements at the caller-visible API/quota boundary for managed services or per inference instance for self-hosting, referencing Stage 4 objectives. Include first-token/token latency for streaming, completion/throughput for task or batch paths and GPU measures only when observable. Name benchmark fixtures, runner, owner and pre-exposure gate; attach available results or mark execution pending. This capacity reference supplies 5.3 app concurrency/admission and owned replica sizing. [AWS workload criteria](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentperf01-bp01.html) (Agentic AI Lens current), accessed 2026-10-01.

**Deployment boundary.** Reference the approved deployment mode in 2.2 and request contract in 3.1. Record service/runtime version, model revision and exposed serving features. Managed APIs use caller-visible controls and provider-owned internal hardware/precision; specify hardware only when self-hosting. Keep serving component provenance within 5.5 security review. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) describes provider-managed caching; [vLLM engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/) describe self-hosted controls (current API / vLLM V1 latest docs, accessed 2026-09-30).

**Select techniques by measured workload.** For controls exposed by the chosen service, specify comparable baseline/candidate benchmark fixtures and expected latency, throughput, cost and quality evidence; attach observations when available, otherwise name pending execution, owner and adoption gate. For self-hosting, candidates can include speculative decoding, continuous batching, KV-cache management and prefix reuse. Reference approved application cache/streaming/tool-call decisions when constructing traffic. vLLM describes speculative gains as dependent on workload/model/hardware; prefix caching saves shared-prefix prefill, not decoding. Preserve approved freshness and quality constraints for response reuse. Label choices provisional until required checks pass. [vLLM speculative decoding](https://docs.vllm.ai/en/latest/features/speculative_decoding/), [automatic prefix caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/), and [benchmark CLI](https://docs.vllm.ai/en/stable/benchmarking/cli/) (vLLM V1 latest/stable docs, accessed 2026-09-30).

**Compression and precision.** For artifacts justified in 2.7, specify deployment compatibility and baseline comparison for task quality, instruction/tool behavior, throughput, latency and cost. Self-hosting adds memory fit and supported hardware/weight/activation/KV formats; managed APIs record provider ownership of unexposed internals. Record proposed values, version support, procedure/fixtures, expected evidence and owner/adoption gate, with available results or pending execution. Lossy choices must pass inherited quality gates; evidence requiring another method reopens 2.7. [vLLM quantization and hardware support](https://docs.vllm.ai/en/stable/features/quantization/index.html) and [TensorRT-LLM quantization](https://nvidia.github.io/TensorRT-LLM/latest/features/quantization.html) (vLLM stable docs / TensorRT-LLM latest docs, accessed 2026-09-30).

**Versioned runtime record.** For vLLM, decide per-instance `tensor_parallel_size`, `max_num_batched_tokens`, `max_num_seqs`, scheduler admission, GPU-memory/KV-cache size and prefix caching, adding a `block_size` override only when benchmark evidence justifies it. Current `block_size` accepts the runtime default; `max_num_seqs` limits sequences in a scheduler iteration and is distinct from a deployment queue limit. Weight offload (`cpu_offload_gb`) moves weights through the CPU-GPU interconnect during forward passes; KV offload (`kv_offloading_size`) controls a separate buffer. Record exact supported parameter values, evidence and rationale; 5.3 owns gateway/dependency admission and replica scaling. [vLLM engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/) (vLLM V1 latest docs, accessed 2026-09-30).

**Capacity evidence.** Specify a representative load-test procedure at the managed API/quota or owned serving-instance boundary: arrivals/concurrency, prompt/output lengths, observable cache state and tool mix, request/token throughput, queue/completion latency and task quality, with conditional streaming/GPU measures. Record expected accepted load under approved objectives, runner/run point, owner/pre-exposure gate and actual results or pending execution. Control or document cache state when observable. Give the versioned plan/results to 5.3; inference replicas are sized only where the application owns them. [vLLM performance dashboard](https://docs.vllm.ai/en/latest/benchmarking/dashboard/), [metrics](https://docs.vllm.ai/en/latest/design/metrics/), and [benchmark CLI](https://docs.vllm.ai/en/stable/benchmarking/cli/) (vLLM V1 latest/stable docs, accessed 2026-09-30).

## Model routing and scaling (5.3)

**Routing as a tested optimization.** Specify a comparable fixed-versus-routed experiment among approved 2.2 model/effort candidates on common, hard and high-impact task categories. Record fixture/environment, runner/run point, expected quality, router overhead, category errors, tail latency, cost-per-success and escalation evidence, plus owner and pre-exposure gate. Attach available results or mark pending; choose provisional eligibility and direct/stronger routes using 2.1 policy and Stage 4 gates, requiring executed acceptance before exposing changed allocations. Intent and capability discovery retain their Stage 2 owners. [Microsoft model-router evaluation](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/evaluate-model-router) (updated 2026-08-20), [OpenAI model selection](https://developers.openai.com/api/docs/guides/model-selection) (API v1/current), and [Anthropic effective agents](https://www.anthropic.com/engineering/building-effective-agents) (2024-12-19), accessed 2026-09-30.

**Replaceable components and state.** Record application gateway/orchestrator replica ownership and durable-state reference from 5.4. Size app concurrency/admission using managed API/quota capacity; size inference replicas only when self-hosting. For selected autoscalers, specify supported resource/custom/external signals, targets, limits and warm-up using 5.2 capacity plan/results, with pending assumptions and validation gate explicit. Record routine overload admission; 5.6 owns pressure overrides. Tail latency is an outcome/SLO signal and may not be a supported scaling input. [Kubernetes Horizontal Pod Autoscaling](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/) (autoscaling/v2, current) and [Azure throttling pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling) (current), accessed 2026-09-30.

**Asynchronous work and shared dependencies.** For work beyond the approved synchronous deadline, choose a supported deployment transport and reference the 3.1 task identifier/status/result/cancellation contract. Record backlog depth/age bounds and deployment of replay-safe consumers. Assign normal-load model request/token, store connection and third-party API rate/concurrency budgets, enforcement owners and admit/wait/reject/defer actions in the shared-resource protection plan. Validate the selected queue/priority behavior against approved workload policy. [Azure asynchronous request-reply pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply), [Azure throttling pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling), and [bulkhead pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead) (current Azure architecture guidance); [OpenAI rate limits](https://developers.openai.com/api/docs/guides/rate-limits) (API v1/current), accessed 2026-09-30.

## State persistence and lifecycle (5.4)

**Storage and durability.** Select a state backend for the actual deployment topology, concurrent writers, consistency needs, recovery point, retention, security, and operating burden. In-memory state loses work on process loss unless another durable component owns it. Redis can use RDB snapshots, AOF, both, or neither; their loss and latency trade-offs differ, so naming Redis alone does not establish durability. SQLite and PostgreSQL are checkpointer options, but topology and concurrency decide fit rather than a universal scale ladder. A managed agent platform may own checkpoint storage; record that contract rather than adding a second conflicting store. [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) and [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/) (current, accessed 2026-09-30).

**Pause window and expiry.** Check deployed service limits and retention against the approval window from 1.3 and data policy from 2.4. Record checkpoint/pending-approval/operation-record lifetimes, deletion job and expired-run outcome in the storage/lifecycle/recovery outputs; audit retention follows the 4.4 capture policy. Expiry produces the approved terminal or fresh-start route. Reopen the approval-window decision if platform limits cannot support it. [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) and [OpenAI Agents SDK human review](https://openai.github.io/openai-agents-python/human_in_the_loop/) (current, accessed 2026-09-30).

**Checkpoint boundaries and contents.** Bind the 3.2 payload to backend, writing cadence and approved sensitivity/minimization controls. For LangGraph, record actual super-step checkpoint and pending-write/interrupt rerun boundaries in the lifecycle sequence. Specify interruption fixtures, procedure, expected preserved outcomes and resumed/failed/expired pending work, owner and pre-exposure gate; attach existing results or pending execution. Do not count a plan as passing deployed recovery evidence. [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) and [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) (current, accessed 2026-09-30).

**Trusted recovery and approval.** Load a trusted checkpoint by run/thread identifier and owner, verify the saved version and pending action, and bind the authorized approver's decision to that exact action and arguments. Claim the continuation once so parallel workers do not both resume it. An approval result is control data, not a free-form model instruction. A historical checkpoint can aid sandboxed debugging; replay after it executes new model and API calls and is not a rollback of completed external effects. [OpenAI Agents SDK human review](https://openai.github.io/openai-agents-python/human_in_the_loop/) and [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) (current, accessed 2026-09-30).

**Side effects and changed facts.** Bind the 3.1 replay contract and 3.2 operation identity to ledger location, atomic claim/persistence and provider key lifetime. Specify ambiguous-result reconciliation tests before retry. For each consequential resume, name live permission/fact/dependency source and check owner, plus approved changed-premise replan, renewed-approval or stop route. Record fixtures/procedure, expected evidence, execution owner/gate and available results or pending execution. A check-then-act record can race or lose a completed remote result. [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests), [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts), and [Azure compensating transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction) (current, accessed 2026-09-30).

**Protocol boundary.** MCP 2026-07-28 has a stateless protocol core, yet an application can persist explicit handles and the Tasks extension supports long-running work. State ownership belongs in the chosen host, platform, or tool contract; do not infer that every MCP integration must replay from a LangGraph checkpoint. [MCP 2026-07-28 release](https://blog.modelcontextprotocol.io/posts/2026-07-28/) (accessed 2026-09-30).

## Release security and compliance checks (5.5)

**Execution and authority.** Specify release-environment tests for approved controls using exact environment/version, fixtures, expected decisions, runner, owner and pre-exposure gate. Model-directed code or untrusted artifacts need applicable isolation and credential-broker checks; ordinary controlled calls need scoped authorization/path checks. Record actual results when available or pending execution; passing deployed evidence is required before exposure. Reference Stage 1 obligations and Stage 2 enforcement; a prompt or tool annotation is not authorization. [OpenAI sandbox security](https://developers.openai.com/api/docs/guides/agents-api/environments/security), [OpenAI plugin security and privacy](https://developers.openai.com/plugins/guides/security-privacy), and [Agents SDK guardrails](https://openai.github.io/openai-agents-python/guardrails/) (current, accessed 2026-09-30).

**Content risk and adversarial testing.** Specify deployed-release checks for approved moderation/refusal/output/action controls using canonical Stage 4 cases and scoring, including unsafe misses and benign false blocks in applicable slices. Select reachable injection/leakage/consequential-action scenarios from 2.9. Record release environment, procedure, expected evidence, owner/gate, mitigation/residual risk and reviewer; attach existing results or pending execution. Passing evidence supplies 5.1 cohort readiness and 5.6 disposition before traffic exposure. [Microsoft Content Safety transparency note](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/content-safety/transparency-note), [OpenAI moderation](https://developers.openai.com/api/docs/guides/moderation), [Agents SDK guardrails](https://openai.github.io/openai-agents-python/guardrails/), and [OpenAI red teaming](https://developers.openai.com/api/docs/guides/red-teaming) (current, accessed 2026-09-30).

**Third parties, secrets, and audit.** During design, vet exact third-party versions, provenance, requested access and update disposition against available public facts. Specify release-environment credential-flow and 4.4 audit collection/redaction/access/retention/deletion checks with fixtures, procedure, expected evidence, owner and pre-exposure gate. Record available results or pending execution. Required checks must pass before exposure; 6.6 later reviews the deployed baseline. [OpenAI plugin security and privacy](https://developers.openai.com/plugins/guides/security-privacy), [OpenAI sandbox security](https://developers.openai.com/api/docs/guides/agents-api/environments/security), and [OpenTelemetry sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/) (current, accessed 2026-09-30).

## Rollback and cost governance (5.6)

**Release decisions and recovery.** Map 4.5 verdicts and 5.1 exposure stages to executable promote/pause/stop/revert actions and operators. Specify traffic/configuration/application recovery and stored-state compatibility tests, plus authorized external-effect reconciliation or compensation with owner/escalation. Record environment/fixtures, runner/run point, expected evidence, owner/gate and available results or pending execution. Provide action IDs and passing recovery evidence to 5.1 before corresponding exposure. [Argo Rollouts analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/), [Google SRE canarying](https://sre.google/workbook/canarying-releases/), and [Azure compensating transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction) (current, accessed 2026-09-30).

**Spend controls.** Within the approved financial objectives and 3.6 per-task enforcement, choose aggregate workflow/traffic-class allocations, protected traffic and alert-only or enforced service limits. Record the enforcement boundary, owner and limit response. Provider hard-limit propagation and usage-reporting delays affect the real ceiling; choose warning headroom and test limit response/restoration. 6.4 observes the selected usage and cost signals. [OpenAI spend limits](https://developers.openai.com/api/docs/guides/spend-limits) (API current, accessed 2026-09-30).

**Measured pressure degradation.** Order approved overrides to normal 5.3 admission/model allocation and 5.2 controls as demand/spend approaches a limit. Specify baseline/candidate tests for quality, freshness, privacy/residency, latency and cost before adopting a substitute. Record trigger, operator, expected/measured effect, owner/gate, pending execution where applicable, stop and restoration rule. Distinguish platform controls from app controls. 6.5 operates failure-specific dependency cutoff/probes using this playbook where needed. [Azure throttling pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling) and [OpenAI deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist) (current, accessed 2026-09-30).

**Cost-accounting and enforcement evidence.** Select usage and billed-cost sources, reporting-delay assumptions, reconciliation owner/cadence and limit-warning headroom in the cost-governance decision. Reference the Stage 4 token/tool/cost-per-success definitions and supply their source/limit references to 6.4, which owns continuous collection and anomaly alerts. Reconcile estimates with billed reports when reviewing whether deployed limits achieved the chosen ceiling. [Claude Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api) (current) and [OpenAI spend limits](https://developers.openai.com/api/docs/guides/spend-limits) (API current), accessed 2026-09-30.

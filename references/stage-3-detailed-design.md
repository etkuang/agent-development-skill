## Integration arguments (3.1)

- Model, selected-trainer, tool, service, and server arguments must be verified against official documentation for the exact model/API version and deployment mode. Record stable parameter/default IDs, consumers, support/verification status, name, type/unit, required/conditional status, documented range/default, chosen value or omission, and rationale with source URL, version, and access date. Stage 2 owns product, role and training-method selection; this aspect supplies exact exposed controls and values.
- Tool input encoding: derive model-facing tool input fields from the authoritative 3.2 artifact schema and record its ID/version. Use the selected API's supported strict JSON Schema subset and bind application validators for constraints that this encoding cannot express; do not define a second domain-field schema. OpenAI's strict function calls require all object properties to be listed as required and `additionalProperties: false`; Anthropic's structured-output mode does not support numerical bounds. Do not assume one provider's accepted schema works on another. Sources: [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), OpenAI API v1, and [Anthropic structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), current Claude API; accessed 2026-09-29.
- Credential flow: choose the selected integration's actual authentication contract. API keys belong in environment variables or a secret manager; account-linked MCP integrations may require OAuth, token refresh, and an authentication challenge. Missing or expired credentials must produce an actionable recovery path without exposing secrets to the model or logs. A hidden-file and `[NEED_KEY]` pattern is a local example, not a universal requirement. Sources: [OpenAI production guidance](https://developers.openai.com/api/docs/guides/production-best-practices), OpenAI API v1, and [OpenAI plugin authentication](https://developers.openai.com/plugins/build/auth), current Plugins/MCP; accessed 2026-09-29.
- Asynchronous operations: select a completion mechanism supported by the operation: polling a task identifier, webhook or callback, or a returned task result. Record deadline, cancellation, terminal statuses, and failure reporting; use bounded poll backoff only for polling. Sources: [OpenAI background mode](https://developers.openai.com/api/docs/guides/background) and [webhooks](https://developers.openai.com/api/docs/guides/webhooks), Responses API v1; accessed 2026-09-29.
- Correctness-relevant model-call controls: specify only controls supported by the chosen model and endpoint, such as reasoning effort, output constraints, token limits, or sampling settings. GPT-6 reasoning calls with effort other than `none` do not accept `temperature`, `top_p`, or `top_logprobs`; newer Claude models also restrict temperature. Temperature zero does not guarantee identical outputs. Treat logit-level controls as provider-specific capabilities, not a default fact-control mechanism. Retrieval depth belongs to aspect 3.4. Sources: [OpenAI GPT-6 model guidance](https://developers.openai.com/api/docs/guides/latest-model), OpenAI API v1 / GPT-6, and [Claude Messages API](https://platform.claude.com/docs/en/api/go/messages/create), current Claude API; accessed 2026-09-30.
- The argument tables cover model and selected-trainer calls, tool calls, and service/server connections; configurable application settings reference their stable parameter/default IDs. Record vendor support/range/default facts here, but bind chosen retrieval values to 3.4 and derived numerical budget/trigger values to 3.6 rather than redefining them. For every selected parameter, include its documented type, unit, required or conditional status, supported range/default (or not specified), proposed value or omission, rationale, source URL, version, and access date. Source: [OpenAI Responses create reference](https://developers.openai.com/api/reference/cli/resources/responses/methods/create) and [OpenAI MCP server guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp), Responses API v1; accessed 2026-09-30.
- Retry strategy: bind each reachable integration failure to its approved 2.3 transition, then record exact per-call replay eligibility, attempt/deadline/backoff limits and corrective handling. Transient 429/503 responses may warrant replay of the same safe request after the provider's `Retry-After` or bounded backoff; validation errors should be returned in actionable form so the model can correct the arguments. Escalate to another model or tool only when the failure needs a different capability or service. Account for SDK retries in the total attempt and time budget. Sources: [OpenAI rate limits](https://developers.openai.com/api/docs/guides/rate-limits), OpenAI API v1, and [Anthropic tool-call errors](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls), current Claude API; accessed 2026-09-29.
- Failure taxonomy for integrations: parameter errors require corrected parameters before a new attempt; permission errors need authorization or a stop; transient service errors may be retried within a deadline or routed to a fallback. An unknown timeout outcome after an external write must be reconciled before replay unless the provider offers an idempotency key or equivalent precondition. Source: [Google Cloud Storage retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy), current Cloud Storage; accessed 2026-09-29.

## Tool and skill description design (3.1)

Formula for a good tool definition: **purpose + boundary + input constraints − when NOT to use**. Worked example (inventory query tool): call when the user asks whether a specific product is in stock in a specific region; require product id and region code; do not use it for price, coupon, or recommendation questions — call the comparison tool instead. Ambiguous descriptions set traps for the model.

Supporting techniques: descriptions are selection features, so explain the user goal, trigger, limits, and exclusions and distinguish neighboring capabilities. Use the coherent action and permission scopes selected in 2.2, keeping read/write capabilities distinguishable in descriptions. If metadata design reveals actions requiring separate permissions or confirmation, revise and reconfirm 2.2 rather than silently creating a new action scope here. Record accurate safety and permission metadata rather than treating every metadata field as a routing feature. Keep the description surface and runtime schema derived from one source where feasible. Sources: [OpenAI tool design](https://developers.openai.com/plugins/plan/tools), current Plugins/MCP, and [OpenAI Skills](https://developers.openai.com/api/docs/guides/tools-skills), Responses API v1; accessed 2026-09-29.

## Node data flow and schemas (3.2)

**Selected-path scope.** The contracts describe the direct API path, code workflow or graph actually chosen. Graph channel/reducer and node-state guidance below applies when a graph is used. For a direct path, record application input/output owners and absent inter-step artifacts without introducing graph state. The data-flow figure can show one executable call and its results. [Anthropic effective agents](https://www.anthropic.com/engineering/building-effective-agents) (2024-12-19), accessed 2026-10-01.

**Inter-node state.** Include a field only when a later node or recovery path needs its value. Keep raw evidence when it is expensive or impossible to refetch; use stable IDs for large content that can be retrieved reliably. Avoid duplicate derivable values or formatted prompt strings in state. In the per-artifact schema table (O-3.2-01), record producer, consumer, owner, lifetime and payload/reference representation. For large retained or referenced content, record continuation justification, retrieval prerequisite and resolution path, availability/lifetime, and size/refetch-cost assumptions for 3.6. [LangGraph state design](https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph) and [checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) (OSS Python current), accessed 2026-09-30.

**State, summaries, and audit.** Execution state carries values needed across steps; audit telemetry is separately scoped to an observability purpose and minimized for sensitive data. Record the named downstream or recovery use supporting each retained field. For data omitted from state, put any remaining telemetry observation need in the O-3.2-01 handoff-needs field for 4.4 to refine into its capture design. A continuation summary may be prose, structured fields, or provider compaction, but must preserve task-critical identifiers, constraints, decisions, action outcomes, and open items. Preserve precise metadata or source references when the workflow needs them; a permanent summary need not carry every tool argument and return. [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (2025-09-29), [OpenAI compaction](https://developers.openai.com/api/docs/guides/compaction) (Responses API v1/current), and [OpenTelemetry sensitive-data handling](https://opentelemetry.io/docs/security/handling-sensitive-data/) (current), accessed 2026-09-30.

**Recovery and side effects.** A selected checkpoint runtime may store state values, next tasks, and write metadata at its own boundaries; the application need not duplicate the entire plan and raw tool I/O in one state object. Map completed work, pending work, required references, and durable action outcome IDs to the selected platform's checkpoint payload and actual resume boundary. The checkpoint record (O-3.2-05) references large-content representation/prerequisite rows from O-3.2-01 and states their resume-availability checks. A resumed node or replay may reissue calls; reference 3.1's provider replay/idempotency contract. Backend topology, pause/expiry, retention and operational resume are refined in 5.4. [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) (OSS Python current) and [OpenAI Agents API recovery](https://developers.openai.com/api/docs/guides/agents-api/errors) (`agents=v1` beta), accessed 2026-09-30.

**Schema boundaries.** Aspect 3.2 owns application/inter-step artifact fields, including domain tool input/result/error fields. Aspect 3.1 binds tool inputs to vendor encoding; aspect 3.3 owns each model output schema. Reuse that model-schema ID when passed unchanged, and define only distinct application projections/adapters here. Distinguish graph state from physical store definitions (3.5) and the later trace/audit observation design (4.4). Identity fields carried in state do not authorize actions; the trusted service checks authority at the action boundary. Name the validation boundary and unit for character, encoded-byte, and model-token limits. Map each Stage 2 node to its producer and consumer fields, including evidence provenance through the final answer. [LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api) (OSS Python current), [OpenAI MCP server authorization](https://developers.openai.com/plugins/build/mcp-server) (current), [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12/json-schema-validation), and [OpenAI token counting](https://developers.openai.com/api/docs/guides/token-counting) (Responses API v1/current), accessed 2026-09-30.

**State and recovery deliverables.** The per-artifact schema table covers field semantics, type, nullability, constraints, producer, consumer, owner, retention/representation decisions, large-content prerequisite metadata and omitted-telemetry observation handoffs. The graph-state description names channels, readers and writers, and update or reducer behavior; it distinguishes input, internal and terminal-output scope. If summarisation is selected, define the retained summary payload, source bindings and precise metadata/evidence references under the correction/retention policy already approved in 2.4. If checkpointing is selected, record the platform contract for checkpoint identity, values, pending tasks and resume boundary, referencing representation rows and resume-availability checks. Label inter-node artifacts and success/failure paths in the Mermaid data-flow figure so it complements the Stage 2 route diagram. [LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api), [memory management](https://docs.langchain.com/oss/python/langgraph/add-memory), and [checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) (OSS Python current), plus [Mermaid flowcharts](https://mermaid.js.org/syntax/flowchart.html) (v12 current), accessed 2026-09-30.

## Prompts and structured output (3.3)

**Prompt contract and context boundaries.** Give each model-driven node a versioned, role-separated prompt template with the task, expected response, terminology, allowed values, input variables, and failure path. Keep runtime values and retrieved/tool content in labeled data slots distinct from trusted instructions; a tool result or another model's answer is not an instruction or a verified fact. Add normal and boundary examples only when they improve evaluated behavior, and make example outputs match the selected schema. A zero-shot prompt can be the first baseline. Do not require a fixed example count, a last-100-token instruction, XML output wrapping, or visible chain-of-thought. [OpenAI prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering), [reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices) (OpenAI API current), and [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) (Claude API current), accessed 2026-09-30.

**Structured-output mechanism and failure states.** For each node, name the selected model/API, the provider-supported schema mode or local grammar, the schema version and accepted subset, and the application validator. Plain JSON mode assures JSON syntax, not adherence to a supplied schema; strict schema modes improve structural reliability but do not prove that the answer is true. Handle refusal, content filtering, incomplete/max-token output, malformed syntax, schema mismatch, and extra prose as distinct outcomes. Validate business constraints and referenced record IDs after parsing. Retry or repair only recoverable errors within an attempt budget; a refusal or policy block is not a malformed JSON object to repair. [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) (OpenAI API v1/current) and [Claude structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) (Claude API current), accessed 2026-09-30.

**Reasoning, decomposition, and semantic review.** Reasoning models can reason internally without a prompt demanding disclosed steps. Write prompts and handoff schemas for the solving/formatting steps approved in 2.3. Record a proposed topology change there when available task evidence justifies it; a prompt does not silently add new executable steps. Name deterministic semantic/business/source validators first. For residual high-risk review, record the authorized reviewer, runtime trigger and reviewed artifact, handing measurement/calibration needs to 4.3. A schema-valid object may still contain a false statement or wrong calculation. [OpenAI reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices), [evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) (OpenAI API current), and [Claude structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) (Claude API current), accessed 2026-09-30.

**Evidence and citations.** Bind factual claims to authorized source IDs, versions, and visible passages; check that cited records exist and actually support the claim. Preserve uncertainty and qualifications. A conversation history item or another model's output can guide the workflow but is not by itself an authoritative source. Design citation delivery with the selected output mode: Claude's native citations cannot be combined with its strict JSON output mode because citation blocks interleave with text, so use a compatible rendering or separate structured evidence field and validate it. [Claude citations](https://platform.claude.com/docs/en/build-with-claude/citations) (Claude API current) and [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) (OpenAI API v1/current), accessed 2026-09-30.

## Retrieval and chunking settings (3.4)

**Applicability.** Carry forward Stage 2's direct-source or indexed route. Record direct no-index/no-chunk decisions and source access/provenance. Segmentation, embeddings, candidate counts and ranking measures below apply only where those stages exist; an exact unranked lookup can mark ranking not applicable while testing evidence and final outcomes. [Bedrock no-chunk option](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html) and [AWS custom-document options](https://docs.aws.amazon.com/prescriptive-guidance/latest/retrieval-augmented-generation-options/options.html) (current), accessed 2026-10-01. Applying those alternatives to the selected direct route is a design inference.

**Chunk candidates and provenance.** Choose no chunking, fixed-size, structural, semantic, or parent-child segmentation from source shape and representative queries. Record boundary rule, size and unit, overlap, stable chunk and parent/source IDs, source version, and available page, section, table, or image locations. A page can be a useful citation location without becoming the mandatory embedding unit. Choose source-specific size candidates and units; no fixed FAQ or technical-document character range is a default for all applications. Azure and Bedrock publish different service-specific starting settings and both allow content-dependent alternatives. [Azure chunking guide](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents) (updated 2026-07-02), [Amazon Bedrock chunking](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html) (current), and [Azure semantic chunking](https://learn.microsoft.com/en-us/azure/search/search-how-to-semantic-chunking) (current), accessed 2026-09-30.

**Context enrichment.** When a retrieved fragment is hard to interpret alone, compare title/heading metadata, parent context, or concise chunk-specific context added to indexed text. Measure retrieval gain, storage/token cost, and risk of misleading generated context. A generic document summary before every chunk is not a universal fix; Anthropic's contextual-retrieval experiments found chunk-specific context more useful than generic summaries. [Anthropic contextual retrieval](https://www.anthropic.com/engineering/contextual-retrieval) (2024-09-19) and [Azure chunking guide](https://learn.microsoft.com/en-us/azure/search/vector-search-how-to-chunk-documents) (updated 2026-07-02), accessed 2026-09-30.

**Query, index, and rank settings.** Carry forward Stage 2's selected direct-source, lexical, structured, vector or hybrid route. If vector search is used, define one stable embedding-configuration record here with model/version, dimensions and index/query compatibility; the physical index in 3.5 references that configuration. For selected query transformations, record the concrete rule, input/resulting query artifact IDs and canonical 3.2 schema IDs in the retrieval/query parameter table (O-3.4-02); keep domain payload fields in 3.2. Preserve exact identifiers and original intent when applying optional follow-up rewriting, synonyms, or filters. Enforce user access and valid source versions before content reaches the model; a reranker is not an authorization boundary. For indexed/ranked stages approved in 2.5, compare concrete setting candidates on local labeled queries within approved latency/cost limits; route architectural changes back to 2.5. Record initial, reranker-input and final counts only for existing stages; a reranker cannot recover missed candidates. Distinguish fixed query plans from runtime iterative retrieval when needed. [Azure hybrid search](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview), [Azure semantic ranker](https://learn.microsoft.com/en-us/azure/search/semantic-search-overview), and [Microsoft RAG retrieval guide](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval) (current Azure guidance, accessed 2026-09-30).

**Local calibration and tuning.** Record focused query fixtures, reference evidence, source/index/setting versions, applicable candidate counts, and the named measure implementation/version used for local comparison. Evidence coverage or context recall diagnoses missing support; rank-sensitive precision or NDCG applies only to ordered candidates. Record available quality/latency/cost observations and failure cases with provenance, or explicitly pending measurement; never invent design-stage results. Hand these local fixtures/measures to Stage 4 for full task coverage, formal definitions and acceptance thresholds. Fixed top-k anecdotes or answer-correctness weights do not generalize. [Microsoft Foundry RAG evaluators](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators) (current), [Ragas context precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/) and [context recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/) (current collections API), accessed 2026-09-30.

## Database configuration and lifecycle (3.5)

- **Physical store definitions and identifiers.** Instantiate approved persistent application stores from 2.2/2.3, memory stores from 2.4, retrieval stores from 2.5 and an answer cache selected in 3.6. Record each logical-store or cache decision reference with its exact physical tables/collections/indexes, storage metadata fields/types, keys/constraints, consistency/query assumptions and migration bindings. If physical configuration cannot satisfy the approved need, reopen its architectural owner. One store can hold operational records and vectors; a separate search index adds a synchronization path. When stores are split, retain stable source and record IDs for joins and deletions. Unchanged application/model payloads reference 3.2/3.3 schemas. Vectorizer dimensions and retrieval/similarity settings reference authoritative 3.4 configuration IDs. [Azure vector-search service choices](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/vector-search) and [Pinecone index creation](https://docs.pinecone.io/guides/index-data/create-an-index) (Pinecone API 2026-07 for document-schema examples), accessed 2026-09-30.
- **Durability and ownership.** Record store/lifecycle/resource owners, the 3.1 connection/credential reference, persistent backend, index/collection ID, schema/index version and startup load path; application resource ownership is wired in 3.7. LlamaIndex's in-memory storage needs explicit persistence; configured remote backends can persist by default. Preserve the source ID and useful PDF page or section location without requiring one vector per page. Do not copy example local filenames into a cross-backend contract. [LlamaIndex persistence and loading](https://developers.llamaindex.ai/python/framework/module_guides/storing/save_load/) (current Python framework), [AWS Secrets Manager hardcoded-secret guidance](https://docs.aws.amazon.com/secretsmanager/latest/userguide/hardcoded.html) (current), accessed 2026-09-30.
- **Initialization and migration.** Define replayable initialization and schema/index versions. Order migration revisions, validate before cutover, and record a recovery point. For incompatible search-index changes, build and test a new index and move an alias after verification. A downgrade is conditional on the selected migration path. [Alembic migration tutorial](https://alembic.sqlalchemy.org/en/latest/tutorial.html) (1.20.0), [Azure AI Search index creation](https://learn.microsoft.com/en-us/azure/search/search-how-to-create-search-index), and [index rebuild guidance](https://learn.microsoft.com/en-us/azure/search/search-howto-reindex) (current), accessed 2026-09-30.
- **Freshness mechanisms.** Reference the approved source-specific freshness/staleness requirement from the source architecture and configure the mechanisms needed to meet it. Detect inserts, updates and deletions; use stable document IDs to skip unchanged content and reprocess changes. Regenerate embeddings when source content or the embedding model changes, record the model/index version, and propagate deletions to derived indexes. Check query visibility after writes in eventually consistent indexes and use a live source for questions whose timeliness exceeds index lag. Change tracking, streams, and TTL are candidate mechanisms, not universal defaults. [LlamaIndex document management](https://developers.llamaindex.ai/python/framework/module_guides/loading/ingestion_pipeline/) (current), [Azure SQL indexer change and deletion tracking](https://learn.microsoft.com/en-us/azure/search/search-how-to-index-sql-database), [Weaviate vectorizer migration](https://docs.weaviate.io/weaviate/tutorials/vectorizer-migration) (Weaviate Cloud v1.32+), and [Pinecone ingestion freshness](https://docs.pinecone.io/guides/index-data/data-ingestion-overview) (current), accessed 2026-09-30.
- **Answer cache and graph state.** For an answer cache selected through 3.6's economic analysis, define its exact physical cache settings, authorized audience and source/index version in the key or validity check. Specify expiry, write invalidation, and a refresh sequence that handles concurrent changes; a version stamp alone does not prevent a stale read. Graph state schema belongs in 3.2, while its checkpoint backend and retention belong in 5.4. [Redis cache-aside](https://redis.io/docs/latest/develop/use-cases/cache-aside/), [Redis caching race conditions](https://redis.io/docs/latest/develop/reference/client-side-caching/), and [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) (current), accessed 2026-09-30.

## Cost and token control (3.6)

**Whole-task accounting.** Trace representative successful, failed, retried, and handoff paths from the Stage 2 workflow. Count calls per node/turn, uncached input, cache writes and reads, output tokens (including any reasoning-token subcategory), tool/schema and Skill payload where billed, external tool fees, and price/version assumptions. Repeated conversation history and tool definitions can dominate long runs; a Skill can add instructions and loaded resources to context. Include total spend and cost per attempted and successful task so failure costs remain visible. Reasoning tokens are part of output billing, not a second charge added on top. [OpenAI Agents SDK usage](https://openai.github.io/openai-agents-python/usage/) (current), [Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing) (current), and [Claude cost and intelligence guide](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence) (current), accessed 2026-09-30.

**Measured control choices.** Prompt-prefix caching discounts repeated input but still invokes the model; semantic response caching can return an old or cross-tenant answer unless similarity threshold, source version, access boundary, and expiry are controlled. For the context-reduction method and preserved-state semantics approved in 2.4, calibrate exact numerical token/cost triggers here using history growth, cache/compaction charges and task-continuity evidence. Record trigger ID, unit/value, rationale, measured/pending status and 3.7 setting consumer; revise the semantic policy in 2.4 only when that policy must change. Compare invalidation/refresh and cache-write costs using the concrete cache mechanism from 3.5, leaving its keys, expiry and concurrency rules authoritative there. Provider automatic/on-demand compaction modes differ, and a smaller context does not always yield a lower bill. Compare model/effort settings and any router to a direct baseline by success quality, latency, and cost per successful task, including tail cases. Fixed compression savings, at-least-50% pruning gain, small-compressor/large-checker pairing, and simple-task-to-small-model route are hypotheses rather than general requirements. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching), [compaction](https://developers.openai.com/api/docs/guides/compaction), and [model selection](https://developers.openai.com/api/docs/guides/model-selection) (OpenAI API v1/current); [Redis semantic cache](https://redis.io/docs/latest/develop/use-cases/semantic-cache/) and [Claude cost guide](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence) (current), accessed 2026-09-30.

**Budget allocation, enforcement and outcomes.** Refine the approved 1.4 end-to-end ceilings into exact phase/call/task latency, token and spend allocations using available traces or explicit estimate assumptions. Record the enforcement point and breach action; changing the ceiling itself returns to 1.4. Distinguish a model's advisory task budget, a per-response output cap, and an application/platform hard stop; an enforced ceiling generally prevents the next call and must account for a call already in flight or a write whose outcome is unknown. Compare total spend, cost per attempt, success rate, and cost per success with the agreed budget and quality/latency gates. Failed or retried runs and the costly tail can make low average token prices misleading. [Claude cost and intelligence guide](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence) (current), [Claude Managed Agents sessions](https://platform.claude.com/docs/en/managed-agents/sessions) (current beta), [OpenAI deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist) (API v1/current), and [AWS Agentic AI cost controls](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentcost07.html) (current), accessed 2026-09-30.

## Application settings, consistency, and readiness (3.7)

- **Executable acceptance and agent evaluations.** Specify runnable checks for settings, artifact adapters, resources and functional interfaces with fixtures, expected results, runner and run point. Record task-outcome and nondeterministic-regression hooks from 1.2 for Stage 4 to expand into full cases and trial protocols; Stage 3 does not require that later approved suite. Test-driven implementation can be a useful practice, but choose implementation test practices according to the project workflow and required verification gates. [Anthropic agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09) and [long-running agent harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) (2025-11-26), accessed 2026-09-30.
- **Durable project handoff.** Keep the current objective, constraints, decisions, next action, acceptance results, and change history in discoverable project artifacts. The next session should inspect those artifacts and the actual repository state before continuing. Anthropic's progress file and Git history and OpenAI's indexed repository documents are examples; no fixed `README`/`PROGRESS`/`tests`/`src` layout or mandatory initializer agent applies to every project. Files can also contain stale or malicious text, so they are evidence to verify rather than automatic authority. [Anthropic long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) (2025-11-26) and [OpenAI harness engineering](https://openai.com/index/harness-engineering/) (2026-02-11), accessed 2026-09-30.
- **Engineering harness for complexity.** For a complex application, make architectural and interface constraints enforceable through lint rules, schema checks, dependency boundaries, or other mechanical tests. Record component/integration check bindings and planned task-evaluation/instrumentation hooks; Stage 4 supplies formal task cases, graders and trace fields. A mandatory black-box-to-white-box transition and four-step coding-evolution ladder are explanatory examples, not requirements. [OpenAI harness engineering](https://openai.com/index/harness-engineering/) (2026-02-11) and [Anthropic agent evaluations](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09), accessed 2026-09-30.
- **Settings and resource ownership.** Record each application setting's source precedence, storage, validator, secret reference, consumer and user-changeability in the setting table (O-3.7-01). Existing call, retrieval, storage and budget values reference their authoritative 3.1–3.6 parameter/default records. For application-only lifecycle, concurrency or presentation settings introduced here, assign stable IDs and own their proposed defaults, allowed values and rationale once under approved constraints. Keep actual credentials out of documents and code. Specify startup and shutdown ownership for clients, tools, sessions, and background work; shared agent/tool objects and restored sessions need a concurrency owner. Bind cancellation to 3.1's protocol, including continuing background work and result reconciliation; hand checkpoint/backend operational-resume needs to 5.4. Bind user-visible progress/final output to the existing schema contract and display each final result once. [Pydantic settings](https://pydantic.dev/docs/validation/latest/concepts/pydantic_settings/) (current), [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/) (current), [OpenAI Agents SDK lifecycle](https://openai.github.io/openai-agents-python/ref/lifecycle/) and [results](https://openai.github.io/openai-agents-python/results/) (current), and [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) (current), accessed 2026-09-30.
- **Consistency map and readiness.** Trace each approved function to its selected workflow step or Graph node, relevant input/output schema, prompt or tool, setting consumer, and acceptance criterion. A Graph node is a real executable component only when a graph is chosen; a single-agent workflow can use a simpler step mapping. At this design stage, specify each planned implementation check with fixture, expected result, runner, owner and run point, and list task-evaluation hooks for later 4.1/4.2 formalization; implementation evidence is gathered later. Mark choices as verified, proposed, or untested and name their decision owner. The readiness list separates resolved design choices from setup prerequisites such as credentials and access, and gives each item an owner, status, and verification gate.

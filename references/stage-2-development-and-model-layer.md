## Intent recognition and routing (2.1)

**Choose routing only when needed.** A single handler, explicit rule, or one agent can cover many approved tasks. Add request classification, specialist handoff, or a layered fallback only after representative cases show that the simpler route fails on task selection, latency, or cost. Rules suit stable, unambiguous cases; a classifier or LLM may help with varied language and context. No fixed rule → small model → large model cascade, model size, or confidence cutoff is a general requirement. Keep route definitions versioned and test changes against a baseline. [Anthropic effective agents](https://www.anthropic.com/engineering/building-effective-agents) (2024-12-19) and [OpenAI practical agent guide](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/) (current guide), accessed 2026-09-30.

**Define route and stop semantics.** Reference approved task/scope IDs, then choose handler boundaries, multi-intent treatment, selection precedence and clarification/abstention/out-of-scope outcomes. Link 1.2's user-visible response and 1.3's authorized handoff contract. Show the independent permission/security check dependency from 2.6/2.9 without redefining its policy or enforcement; 2.3 places the executable transition. A route score cannot override those checks. [OpenAI practical agent guide](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/), [Agents SDK guardrails](https://openai.github.io/openai-agents-python/guardrails/), and [Agents SDK handoffs](https://openai.github.io/openai-agents-python/handoffs/) (current SDK), accessed 2026-09-30.

**Use confidence only with evidence.** A classifier's score is not automatically a probability of correctness. If a numerical score drives routing, fit or check calibration on held-out cases and choose decision thresholds according to the cost of misroutes versus clarification or human handling. Evaluate multi-intent and changed-domain cases rather than assuming a mandatory OOD binary model or daily training loop. LLM self-reported confidence is not calibrated by this classifier procedure. [scikit-learn probability calibration](https://scikit-learn.org/stable/modules/calibration.html) and [decision thresholds](https://scikit-learn.org/stable/modules/classification_threshold.html) (scikit-learn 1.9.1), accessed 2026-09-30.

**Scale tool and Skill discovery when the catalog needs it.** Use 2.2's selected capability purposes/scopes and provisional selection examples to compare direct selection with deferred loading or candidate retrieval when context pressure or selection failures warrant it. Record the discovery strategy and candidate handoff, then hand exact name/trigger/exclusion requirements to 3.1 for refinement and verification. Capture validation needs for candidate recall, final selection/task outcome, harmful mis-execution and overhead; 4.2 supplies formal metrics. Tool-search provider/endpoint support is verified by 2.2; the 100 → 20 → 5 → 1 funnel is an example. [OpenAI tool search](https://developers.openai.com/api/docs/guides/tools-tool-search) (Responses API v1/current), [Claude tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool) (current Claude API), and [OpenAI Skill concepts](https://developers.openai.com/plugins/concepts/skills) (current), accessed 2026-09-30.

## Context and memory design (2.4)

**Memory classification.** Decide first whether the workflow needs only active/session state or approved cross-session memory. Thread-scoped state can itself be persisted for resume; cross-session records have a different recall scope. Classify candidate content by purpose (facts, episodes, instructions), then choose an access pattern and store: structured JSON or key-value lookup for precise facts, semantic search when needed, or a graph when relations justify it. None of these stores is mandatory. List prohibited content and retention/access rules before enabling writes. [LangGraph memory overview](https://docs.langchain.com/oss/python/concepts/memory) (OSS Python current) and [Microsoft memory safety](https://learn.microsoft.com/en-us/security/zero-trust/sfi/manage-agentic-memory-safety) (updated 2026-06-03), accessed 2026-09-30.

**Store policy.** Candidate cross-session records include explicit stable preferences, project decisions with rationale, and actionable feedback with rule, reason, scene, scope, and provenance. Do not infer a sensitive persona or store irrelevant private judgments. Session state may include raw dialogue or tool results for continuity under its own retention policy; project files, code paths, Git history, and configuration may be legitimate task evidence but normally stay in their canonical source rather than being copied into a user profile. Keep only the fields that improve future decisions, with correction and deletion routes. [LangGraph memory overview](https://docs.langchain.com/oss/python/concepts/memory) (OSS Python current) and [Microsoft memory safety](https://learn.microsoft.com/en-us/security/zero-trust/sfi/manage-agentic-memory-safety) (updated 2026-06-03), accessed 2026-09-30.

**Memory architecture.** Choose logical persistence/recall patterns and separate context assembly from memory read/write flow. Define when needed content returns to context, including dialogue references and changed intent, in the layer table and diagram. Conflict/consolidation policy uses source authority, scope and effective time in the store-policy table. Permission checks come from 2.6 and poisoning/instruction-origin controls from 2.9; physical record/store configuration is refined in Stage 3. [LangGraph memory overview](https://docs.langchain.com/oss/python/concepts/memory) (OSS Python current) and [AgentCore preference consolidation](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-user-prompt.html) (current), accessed 2026-09-30.

## Permission architecture (2.6)

**Choose the acting identity.** Interactive access to user-owned data should carry a verified user identity and delegated authority where supported. A scheduled or autonomous agent instead needs its own narrowly scoped identity and accountable owner. Define who the downstream service sees as the subject and actor, with consent and expiry behavior. A shared privileged account must not erase the user's boundary. Confirm the selected identity mode, scopes, consent, enforcement owner for every protected path, and denied-path tests before implementation. Microsoft Agent 365 distinguishes on-behalf-of and service-to-service modes; it is an example of the decision, not a required identity provider. [Microsoft Agent 365 identity](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/identity) (updated 2026-08-13) and [secure multitenant RAG](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/secure-multitenant-rag) (current), accessed 2026-09-30.

**Enforce at trusted data and tool boundaries.** Apply document, row, and field permissions in the source system or a trusted gateway on every reachable retrieval and execution path, before protected content is put into model context. A warehouse row policy, source ACL, gateway check, or server-enforced MCP scope may be the right point for a particular path. Prompts and classifier labels are never the enforcement point. Apply default deny and least privilege; test denied principals and alternate tool routes. [Microsoft secure multitenant RAG](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/secure-multitenant-rag), [OpenAI MCP server guidance](https://developers.openai.com/plugins/build/mcp-server), [OpenAI plugin security](https://developers.openai.com/plugins/guides/security-privacy), and [AWS IAM evaluation logic](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html) (current), accessed 2026-09-30.

**Keep indexed authorization current.** Protected indexed content needs policy-relevant permission metadata at the document or chunk scope required by the source's access model. Filter on verified user, group, tenant, or resource context before returning candidate content, and specify how ACL changes and removals propagate to the index. Do not invent a universal department/classification/owner triplet for every chunk or send an identity vector to the model as a permission check. Azure AI Search's 2026-08-01-preview API illustrates query-time ACL/RBAC enforcement and notes that stale ACLs require index refresh; verify production suitability for the selected service. [Azure AI Search document access](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview) and [query-time enforcement](https://learn.microsoft.com/en-us/azure/search/search-query-access-control-rbac-enforcement) (2026-08-01-preview), accessed 2026-09-30.

**Minimize exposed data and audit decisions.** Choose permission-related masking/redaction where 1.4 requires exposure minimization, retaining underlying trusted authorization. Record protected-access decision/outcome audit hooks in the enforcement map under 1.4's access/retention policy; 4.4 refines concrete event fields. The permission matrix owns principal/resource/action/condition/decision rules and the map owns ingestion/retrieval/source/execution enforcement points. ## Model layer: fine-tuning, alignment, and compression (2.7)

**Availability and baseline before training.** Define the task gap with held-out cases, then test the best feasible untuned model with prompting, supported structured output, tool design, and retrieval for external knowledge. Check provider, model, region, and account access before promising a training job. OpenAI announced a wind-down of self-serve fine-tuning in 2026: organizations new to fine-tuning cannot create jobs, and remaining active customers lose new-job creation on 2027-01-06. Other providers, including Amazon Bedrock, document model-specific customization options. A fixed-format output alone may be solved by structured-output support without training. [OpenAI model optimization](https://developers.openai.com/api/docs/guides/model-optimization), [structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs), and [fine-tuning deprecations](https://developers.openai.com/api/docs/deprecations) (OpenAI API current, 2026-05-07 notice); [Amazon Bedrock model customization](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-models.html) (current Bedrock), accessed 2026-09-30.

**Method choice.** For trainable open-weight models, compare full fine-tuning, LoRA, and QLoRA on task quality, GPU memory, duration, and cost. LoRA trains low-rank adapters while leaving the base frozen; QLoRA loads the base in four-bit precision and trains adapters, reducing training memory. Neither a fixed model-size bucket nor a universal quality, speed, or forgetting percentage determines the method. Managed-model choices are limited to the provider's current supported methods. Quantisation can also serve inference memory/latency goals, and distillation can create a smaller student; neither requires the other to happen first. [Hugging Face PEFT methods](https://huggingface.co/docs/peft/en/methods/overview), [TRL PEFT integration](https://huggingface.co/docs/trl/peft_integration), [Amazon Bedrock customization](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-models.html), and [TensorRT-LLM quantisation](https://nvidia.github.io/TensorRT-LLM/latest/features/quantization.html) (current docs, accessed 2026-09-30).

**Retained capabilities and training controls.** Identify target/retained capability checks and model-level mitigation candidates in the comparative and retained-capability plans. Aspect 2.8 chooses held-out/replay datasets and 4.2 formal regression gates. Verify exposed trainer controls/defaults and choose fix/search/omit strategy with validation/task selection criteria; 3.1 refines exact training arguments. Learning-rate/batch/epoch/schedule choices depend on method/provider rather than portable recipes. [OpenAI fine-tuning best practices](https://developers.openai.com/api/docs/guides/fine-tuning-best-practices), [Amazon Bedrock model hyperparameters](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-models-hp.html), [Hugging Face TRL PEFT integration](https://huggingface.co/docs/trl/peft_integration), and [replay/regularization study](https://arxiv.org/abs/2306.10181) (current docs / study v1, accessed 2026-09-30).

**Long input and modality.** Compare supported training context and modality methods with the long-input task and 2.8 example-length evidence. Choose context extension or adapters only for supported measured needs and record evidence-preservation constraints for 2.8 sequence preparation. That data section chooses truncation/splitting/packing; 3.1 refines exact supported limits/arguments. Sparse attention, gradient checkpointing and mixed precision remain candidate methods, not universal requirements. [Hugging Face TRL memory guidance](https://huggingface.co/docs/trl/reducing_memory_usage) and [Amazon Bedrock model support](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-models.html) (current docs, accessed 2026-09-30).

**Alignment and evaluation.** Choose a supported supervised, preference or reward-based method according to measured behavior gap and available data/grader prerequisites. Define a fair changed-model versus strongest untuned comparison on the same 2.8 held-out datasets using approved 1.2/1.4 acceptance/constraint needs, then hand formal metrics/gates and expert/calibrated scoring refinement to 4.2/4.3. Record target/retained quality, safety, latency, cost and memory checks in the comparison protocol without creating a second dataset or evaluator plan. [OpenAI DPO](https://developers.openai.com/api/docs/guides/direct-preference-optimization) and [reinforcement fine-tuning](https://developers.openai.com/api/docs/guides/reinforcement-fine-tuning) (legacy OpenAI fine-tuning guides, subject to the [2026 wind-down](https://developers.openai.com/api/docs/deprecations)); [Amazon Bedrock reinforcement fine-tuning](https://docs.aws.amazon.com/bedrock/latest/userguide/reinforcement-fine-tuning.html) and [evaluation](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation.html) (current Bedrock docs), accessed 2026-09-30.

## Security and isolation (2.9)

- **Map reachable boundaries.** Map actual input/provenance, executor, network and durable-store trust boundaries to reachable threats. Choose injection, argument/result validation, error-exposure and approval-integrity controls with owner, planned evidence and residual risk in the threat/control table. Consume 2.6's acting identities and authorization map; this security table does not define another permission matrix. [OpenAI plugin security](https://developers.openai.com/plugins/guides/security-privacy) (current) and [OWASP threat modeling](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html) (current), accessed 2026-09-30.
- **Isolate execution where it exists.** Choose executor process/user/data separation, filesystem/network/host resource scope and credential boundary for model-directed or untrusted execution. Record rationale and owner for each path. Controlled functions or remote connections can consume 2.6's server-side authorization without a separate code sandbox. Third-party version/provenance review is recorded as an untrusted-component control in the threat table. [OpenAI Agents API architecture](https://developers.openai.com/api/docs/guides/agents-api/architecture), [sandbox security](https://developers.openai.com/api/docs/guides/agents-api/environments/security), and [OpenAI plugin security](https://developers.openai.com/plugins/guides/security-privacy) (current), accessed 2026-09-30.
- **Treat lower-trust content as data.** Webpages, retrieved files, tool outputs, and third-party tool descriptions may carry instructions that try to redirect the agent or leak data. Do not promote their text into policy or action authority. Validate model-proposed tool arguments on the server and check source, shape, and relevance before external results justify consequential actions. Route/action policy checks remain independent of a classifier score. [OpenAI deep research prompt-injection guidance](https://developers.openai.com/api/docs/guides/deep-research) and [OpenAI plugin security](https://developers.openai.com/plugins/guides/security-privacy) (current), accessed 2026-09-30.
- **Keep credentials out of model-visible paths.** Do not ask users to paste keys or passwords into chat. Use a trusted secret manager, platform vault, account-link flow, or scoped server-side credential broker appropriate to the selected integration. An environment variable is acceptable only when its process and diagnostics cannot expose it to model-directed execution; a restricted file is likewise not safe merely because of its path. Define access scope, rotation, revocation, and what incident triggers a key change. Do not include tokens in prompts, tool results, trace payloads, or errors. [OpenAI sandbox security](https://developers.openai.com/api/docs/guides/agents-api/environments/security), [OpenAI plugin security](https://developers.openai.com/plugins/guides/security-privacy), and [OWASP secrets management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) (current), accessed 2026-09-30.
- **Protect persistent memory.** When durable memory exists, choose source-provenance and instruction-origin checks, poisoning prevention and risk-selected review for behavior-changing entries. Reference 2.4's content/retention/correction contract and 2.6's access controls instead of redefining them. Record traceable correction/recovery interfaces for 6.3's operating contamination response. If memory is absent, state that the memory trust controls are unused. [Microsoft agentic memory safety](https://learn.microsoft.com/en-us/security/zero-trust/sfi/manage-agentic-memory-safety) (updated 2026-06-03), accessed 2026-09-30.
- **Gate actions and sanitize errors.** Consume action approval triggers, reviewer/windows and denial policy from 1.3 and permission checks from 2.6. Choose exact-action/argument/call-identity binding and rejection of mismatched or expired decisions as security controls. Consume 2.3 failure categories while choosing safe category/cause/correlation exposure and protected operator diagnostics. Stage 3 refines typed contracts and 5.4 deployed resume integrity.

# Stage 4 — Evaluation: Technique Reference

Technique guidance supported by public documentation and website sources. This file supports aspects 4.1–4.5 of `SKILL.md`.

## Aspect ownership and handoffs

| Aspect | Authoritative detail | Inputs and handoff |
| --- | --- | --- |
| 4.1 | Canonical task/calibration/grader-validity cases, fixtures/expected labels, coverage, solvability and dataset splits/change lineage | Expand approved early seeds and Stage 3 local fixtures; bind trial requirements to 4.2 and graders to 4.3; provide dataset revisions to 4.5 |
| 4.2 | Formal metric definitions, repeated-trial policy, baselines, thresholds, evidence conditions and hard no-go designations | Operationalize business acceptance and Stage 3 diagnostics; pass metric/criterion IDs to graders, observations and execution |
| 4.3 | Grader implementations/rubrics, state comparators, executable calibration/validity plans, evidence status and trajectory extraction | Consume canonical 4.1 cases, 4.2 definitions and 4.4 observations; require measured human-calibration before cheaper judge adoption and validity evidence before grader use; give per-grade cost/eligibility and valid versions to 4.5 |
| 4.4 | Trace/audit fields/capture, linkage, usage/rate inputs, privacy/export and diagnostic replay | Consume metric/grader observation needs and existing state/user-output contracts; hand executable completeness/privacy/export-access checks, available or pending evidence and pre-exposure gates to 4.5 |
| 4.5 | Pinned run manifests, affected/full CI execution, online sampling, comparability and pass/fail/inconclusive verdicts | Reference criteria in 4.2 without copying them; hand evidence/verdicts to Stage 5 deployment promotion/stop/recovery owners |

The evaluation document adds complete test and measurement detail to approved design inputs. Specify executable procedures, fixtures, runners, run points, expected evidence, owners and gates; attach actual versioned results where available and mark unexecuted checks pending. Pending design evidence does not satisfy a required pre-adoption, pre-use or pre-release gate. Local parameter calibration in Stage 3 remains useful evidence; Stage 4 defines the full protocol and acceptance evidence. Evaluation verdicts and deployed traffic/recovery actions are distinct decisions.

## Evaluation cases and datasets (4.1)

**Start early, then build the full set here.** Stage 1 should capture a small seed of representative real tasks, desired outcomes, and constraints before prompts and architecture harden. Aspect 4.1 expands that seed and Stage 3 local fixtures into complete versioned cases and coverage; grader implementations belong to 4.3 and repeatable run execution to 4.5. Collect real user tasks, support tickets, logs, expert-authored cases, and observed failures; labeled synthetic and adversarial cases can fill missing coverage. There is no universal 50–100-case entry requirement: size depends on task diversity, risk, and the size of the effect a comparison must detect. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09) and [OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) (current API guide), accessed 2026-09-30.

**Make every case solvable and gradeable.** Record canonical case ID and purpose (task, judge-calibration or grader-validity), fixture and expected-label versions, provenance, approved task segment, initial input and environment, available tools/data, acceptable outcome or end state, required and prohibited constraints, and the 4.3 grader ID/version rather than another embedded grader definition. A known working solution or expert check can reveal a broken setup or an ambiguous grader. Case expectations need not demand one exact wording or one tool path if several valid results satisfy the task. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09), accessed 2026-09-30.

**Cover actual capabilities and risks.** Build a matrix from the approved segments and reachable workflow steps, not a compulsory four-box taxonomy. Include representative happy paths, boundary requests, partial outcomes, permission failures, missing evidence or parameters, tool timeouts, and prompt injection where those are realistic. Pair cases where a tool, Skill, search, or refusal should occur with cases where it should not. Tool removal, confusing tool names, and unavailable-capability probes are useful only when those failure modes matter. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09) and [OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) (current API guide), accessed 2026-09-30.

**Repeat and version comparisons.** Model outputs and tool trajectories can vary between trials. Tag high-variance or decision-critical cases and bind their repeat requirements to the policy defined in 4.2. Record case/fixture environment and configuration needs for the pinned 4.5 run manifest; this aspect does not independently choose trial counts or version pinning. Temperature zero does not guarantee reproducibility and some current models reject custom temperature. Add production failures and newly approved tasks through a versioned review, preserving comparison splits and labels. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09), [OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices), and [Claude Messages API](https://platform.claude.com/docs/en/api/go/messages/create) (current), accessed 2026-09-30.

## Metrics and acceptance thresholds (4.2)

**Primary outcome and guardrails.** Name the primary task-success measure and define its ground truth: a final answer, a verified environment end state, or both. For multi-turn work, report consistency over an explicit repeated-trial policy rather than treating one lucky run as representative. Record quality, required process, latency, cost, and safety constraints as guardrails or diagnostics only where they affect acceptance. A support task may require a completed transaction, an authorized tool path, an appropriate explanation, and a bounded number of turns; these are separate observations. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09), accessed 2026-09-30.

| Role | Example measure | Ground truth or observation |
| --- | --- | --- |
| Primary outcome | Task success; environment end-state match | Approved expected outcome and persisted state when actions change data |
| Quality guardrail | Factual correctness; groundedness; interaction quality | Reference answer, cited evidence, or calibrated expert rubric |
| Process guardrail or diagnostic | Correct tool and arguments; prohibited action; recovery; steps or turns | Trace and task-specific required or forbidden behavior |
| System and cost guardrail | End-to-end and tail latency; token use; cost per successful task | Timed trials and metered resource use at representative load |
| Safety or compliance guardrail | Violation rate; false positive and false negative interception | Reviewed policy cases, including allowed and disallowed examples |

**Workflow-specific process and routing metrics.** When routing exists, report per-intent task success and mis-execution, especially for critical intents; overall accuracy can hide a weak high-risk segment. When tools or permissions matter, define selection, argument correctness, unauthorized-attempt and actual-side-effect measures with exact trace/state observations and denominators; 4.3 implements their scoring. Measure recovery and interaction turns only when they diagnose a defined failure mode. Do not infer task success by multiplying per-call accuracy values unless independence and all-calls-critical assumptions have been established. [Ragas agent/tool metrics](https://docs.ragas.io/en/v0.4.1/concepts/metrics/available_metrics/agents/) (v0.4.1) and [OpenAI evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals) (current Agents SDK), accessed 2026-09-30.

**Retrieval metrics.** Name the implementation and reference data before using a metric label. In current Ragas collections metrics, context recall measures the fraction of reference-answer claims supported by retrieved contexts. Context precision is rank-sensitive: it averages precision at relevant ranks, so `relevant chunks / all retrieved chunks` is not the Ragas formula. Answer correctness combines factual overlap and semantic similarity with configurable weights; no fixed 0.75/0.25 mix applies to every project. Measure answer groundedness against retrieved evidence separately from whether it matches a reference answer. Evaluate the concrete retrieval settings from 3.4 using formal reference/groundedness measures, adding ranking metrics only for ordered candidates; recommend parameter changes to the 3.4 owner instead of selecting them in the metric definition. [Ragas context recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/), [context precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/), and [answer correctness](https://docs.ragas.io/en/v0.4.0/concepts/metrics/available_metrics/answer_correctness/) (current collections API / v0.4.0), accessed 2026-09-30.

**Capacity, cost, and model changes.** Measure latency at the user-relevant boundary and report a tail percentile as well as typical latency where delays matter. Track token and tool consumption, plus cost per successful task, rather than cost per request alone. For tuned, distilled, or quantized variants, compare on the same task and retained-capability sets; use training/validation loss as overfit diagnostics and choose classification, generation, or business metrics for the actual task instead of a universal list. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) and [OpenAI model optimization](https://developers.openai.com/api/docs/guides/model-optimization) (current API guidance), accessed 2026-09-30.

**Acceptance criteria and compliance.** Give each gating criterion a stable ID and predeclare its baseline, task segment, threshold/regression margin, measurement window, minimum evidence and hard no-go designation here. Other aspects reference this authoritative contract. A fixed 2% task-success drop or any observed hallucination increase is not a universal rule; small observed changes can be sampling noise. For safety filters, assess both missed harmful content and blocked harmless content on the deployment's own data, then set thresholds by risk. A confirmed hard breach fails evaluation under 4.5; deployed exposure/promotion/stop/recovery actions and exception owners are refined in Stage 5. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [Google SRE error-budget policy](https://sre.google/workbook/error-budget-policy), and [Microsoft Content Safety transparency note](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/content-safety/transparency-note), accessed 2026-09-30.

## Judges and scoring methods (4.3)

**Grader choice.** For each metric ID from 4.2, record an executable, versioned grader with evidence/input and score/output bindings. Choose the cheapest reliable scoring method: deterministic assertions or end-state checks for verifiable outcomes, a validated similarity metric only where similarity is meaningful, and a written model rubric or expert review for open-ended quality. Embedding similarity is not a mandatory middle layer. A task that changes data is checked against the actual database, file, or sandbox state; a final message claiming success is insufficient. Grade tool use or interaction style in addition to the outcome only where the task contract requires it. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09) and [OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) (current guide), accessed 2026-09-30.

**Judge policy and cost.** Where a model judge is necessary, start with a capable judge and define an executable calibration plan in O-4.3-02 using canonical 4.1 case, fixture and expected-label versions; request missing cases there. Record rubric, runner/run point, expected evidence, owner, adoption gate, adjudication and recalibration triggers. Bind agreement and serious-error measurements by task segment to 4.2 definitions/thresholds. Attach actual candidate-versus-human results with versions/provenance when available; otherwise mark execution pending with its owner and gate. A cheaper judge remains a candidate until measured expert-human calibration passes the agreed thresholds. Recheck agreement when tasks, models, or rubrics change. Record eligible criterion/case types, per-grade tokens/calls/cost and calibration/adjudication overhead; 4.5 uses these estimates for total run/online coverage. Name the authorized expert reviewer/adjudicator for high-stakes disagreement. [OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) and [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), accessed 2026-09-30.

**Robustness against bad graders.** Specify an executable validity procedure using canonical 4.1 cases for plausible wrong answers, unsupported claims and scoring-shortcut attacks; submit missing-case requirements to 4.1. For every selected grader, record the general validity plan in O-4.3-01: fixture IDs, runner/run point, expected decisions, abstention/adjudication where applicable, actual evidence or pending execution, owner and a required pre-use gate. Reference model-judge calibration/validity details in O-4.3-02 and applicable trajectory rules in O-4.3-03. Inspect traces and grades to distinguish task failure from a grader rejecting a valid approach. Require an exact sequence or shortest path only when it is part of the task contract. A model judge may abstain when evidence is insufficient. Multi-judge consensus is an option when it demonstrably improves a high-stakes decision, not a universal requirement. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), accessed 2026-09-30.

**Failure attribution and trajectory scoring.** Specify how the evaluator extracts step-level observations to distinguish wrong routing, planning, tool arguments/results, missing retrieval evidence and unsupported generation from defective grading. Bind each process score to 4.2 metric IDs and 4.4 fields, with required/prohibited constraints, optional valid paths and missing-evidence handling. Controlled component tests or mocked dependencies help isolate a suspect step when the system actually has that boundary; confirm any fix on the full workflow. For multi-agent synthesis, judge the integrated result against its task rubric and inspect the orchestration trace only for required handoffs, safety, and efficiency constraints. Apply the process metrics defined in aspect 4.2 while accepting other valid paths. Compare versions on the same representative tasks when practical. [OpenAI evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals) (current Agents SDK guidance) and [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), accessed 2026-09-30.

## Observability and tracing (4.4)

**Link spans and compute usage.** Correlate request, workflow step, model call, tool invocation, handoff, and audit events with safe run/span/parent IDs, status, start/end times, version, and error category. Capture provider usage, priced-tool events and rate/version inputs where available; the accounting pipeline supplies the formal 4.2 cost measure instead of defining a second formula or assuming cost exists on every span. A trace should support task and release metrics without requiring full raw prompts or tool payloads. LangSmith or another tracing backend is optional, chosen for the deployed stack. [OpenAI Agents SDK tracing](https://openai.github.io/openai-agents-python/tracing/), [usage](https://openai.github.io/openai-agents-python/usage/), and [OpenTelemetry GenAI attributes](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/) (current SDK/semantic conventions), accessed 2026-09-30.

**Observe the actual decision path.** Record selected route, plan version or revision, tool and permission decisions, source IDs, outcome, retries, recovery or compensation, and loop detections when those concepts exist. Link each event to the triggering attempt and reason. Track counts and latency by actual component rather than a fixed gateway/router/generation template. Define diagnostic event fields and operator/auditor access here; bind user exports to the existing 3.2 application schemas and 3.7 display path without redefining their fields or rendering. Raw hidden chain-of-thought is not generally available through current APIs; a provider-supported reasoning summary can be captured only when useful and permitted. [OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning) (Responses API v1/current) and [OpenAI Agents SDK tracing](https://openai.github.io/openai-agents-python/tracing/) (current), accessed 2026-09-30.

**Treat replay as a controlled investigation.** Capture references to authoritative 3.2 state transitions, source versions and durable action outcomes needed to explain a failed run; keep checkpoint payload/backend definitions in their design/deployment owners. For a replay, use a sandbox or stubbed tools and mark the historical checkpoint; do not treat state rewind as undoing a payment, deletion, or other external effect. LangGraph re-executes downstream nodes, including LLM and API calls and interrupts, so exact output reproduction is not promised. Checkpoint and trace retention follow the data policy. [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) (current), accessed 2026-09-30.

**Minimize and protect captured data.** The trace schema states field purpose, capture mode, sensitivity, audience, retention, and deletion. Prefer identifiers and summaries to raw prompt, document, tool arguments/results, or error bodies. Apply an allowlist or omission policy and sanitize errors before export; if required redaction fails, the exporter must drop the affected sensitive record or batch rather than leak its original content through another processor. Restrict operator/auditor access and bind an allowlisted transformation to existing user provenance/action-summary artifacts; source/citation schemas and rendering remain in 3.2/3.3/3.7. In the export-access record (O-4.4-03), specify fixtures, runner/run point, expected evidence, owner and a pre-exposure gate for allowlist/redaction, operator access and user-safe projection tests. Attach available versioned results or explicitly mark execution pending; verify the implemented boundary before exposing its exports or approving release. [OpenTelemetry sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/) and [OpenAI Agents SDK tracing/redaction](https://openai.github.io/openai-agents-python/tracing/) (current), accessed 2026-09-30.

**Tie traces to evaluation.** Each release-gating measure needs a declared observation from the trace or verified environment state. Consume omitted-telemetry observation needs from O-3.2-01 and refine their capture fields here when required. Record executable completeness/privacy verification hooks and their available or pending evidence status for 4.5; pending export-access tests retain their owner and pre-exposure gate. If a measure is unobservable, revise captured fields here or reopen its 4.2 criterion before execution. Reference the authoritative acceptance criterion instead of defining another threshold in the trace design. [OpenAI agent evaluations](https://developers.openai.com/api/docs/guides/agent-evals) (current), accessed 2026-09-30.

## Evaluation versioning and CI gates (4.5)

**Version a comparable run.** Record dataset and split, case labels, grader/rubric, prompt, tool/schema, model snapshot, and supported settings with each result. CI can run tests affected by a change and a declared full release suite; expensive model judging need not run on every commit if an earlier reliable gate catches the same failure. When examples or labels change, review the new version, preserve a pinned comparison set or explicitly rebaseline, and report the effect on scores. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) (2026-01-09), [OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices) (current), and [LangSmith dataset management](https://reference.langchain.com/python/langsmith/client/Client) (current SDK), accessed 2026-09-30.

**Execute criterion contracts and report verdicts.** For each criterion ID defined in 4.2, bind the runner to its authoritative baseline, threshold, window and evidence requirement rather than copying those definitions. Specify comparability/evidence checks and pass/fail/inconclusive verdict, reviewer/retest route and result identity. A new version need not improve every measure and one noisy decline does not define rollback. A confirmed hard breach fails evaluation; inconclusive evidence requires measurement/review. Stage 5 decides deployed exposure and recovery. [Anthropic agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [Google SRE canarying](https://sre.google/workbook/canarying-releases/), and [Argo Rollouts analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/) (current), accessed 2026-09-30.

**Split synchronous controls from online quality measurement.** Schedule and verify the approved authorization/safety controls at their existing action-boundary enforcement hooks; their authority/policy mechanics remain in Stage 2. Evaluate risky or representative outputs and traces at a coverage level justified by harm, traffic, statistical evidence, and judge cost; asynchronous sampled quality grading may be appropriate. There is no universal requirement to run an expensive model judge on all high-risk traffic or to sample exactly 5% of routine requests. State segment/eligibility, asynchronous sampling/count rule, the 4.2 evidence-condition reference, missing/harmful-result route and total cost using 4.3 per-grade estimates. [OpenAI Agents SDK guardrails](https://openai.github.io/openai-agents-python/guardrails/) and [LangSmith online evaluation](https://docs.langchain.com/langsmith/online-evaluations-llm-as-judge) (current), accessed 2026-09-30.

**Comparable evidence and deployment handoff.** Compare candidate/baseline runs on equivalent cases; later deployment can supply versioned cohort labels for online comparison, including applicable missed-harm/false-block measures. Verify reviewed dataset/grader changes, preserve a pinned comparison set or authorized rebaseline, and report comparability with the evaluator verdict and evidence package. Hand results to Stage 5's exposure/release/recovery owner; compensation or forward repair for external effects and schema/data changes is specified there. [Google SRE canarying](https://sre.google/workbook/canarying-releases/) and [Argo Rollouts analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/) (current), accessed 2026-09-30.
